## 第一阶段 · 安全审计与加固

源于「扫描项目、审计代码、找 bug」的排查。发现的问题以**实测复现**为准，非静态推测。

### P0-1 越权写入：写接口完全裸奔

**现象（实测复现）**：注册一个**零角色**测试账号登录后，直接调用 `POST /api/clue/remark` 返回 `code=200`——增删改成功。任何持合法 token 的用户都能篡改任意线索备注、任意交易、任意阶段历史。

**根因**：`ClueController` / `TranController` / `CustomerController` 的一批写接口既无 `@PreAuthorize`，也无归属校验。与 `ActivityController`（有「只能修改自己创建的备注」校验）形成双重标准。

**修复**：逐一补齐 `@PreAuthorize`，**权限码严格对齐前端 `v-hasPermission` 指令**（先扫描全部前端按钮指令建立映射，避免「前端可见、后端 403」的割裂）：

| 接口 | 补齐权限 | 依据 |
|------|---------|------|
| `GET /api/clue/{phone}` 手机号查重 | `clue:add\|edit` | 仅录入/编辑表单调用；防手机号枚举泄露 |
| `GET /api/clue/remark` | `clue:view` | 跟进记录含客户隐私，与查看详情同级 |
| `POST/PUT /api/clue/remark` | `clue:edit` | 跟进记录＝对线索的编辑 |
| `DELETE /api/clue/remark/{id}` | `clue:delete` | 与删线索一致 |
| `POST /api/clue/customer` 线索转客户 | `clue:edit` | 不可逆转化（线索 state 置 −1），属高阶编辑 |
| `GET /api/customer/options` | `tran:add\|edit` | 仅新建/编辑交易页需要 |
| `POST/PUT /api/trans` | `tran:add\|edit` | 交易增改 |
| `DELETE /api/tran/{id}\|batch` | `tran:delete` | 交易删除 |
| `POST /api/tran/stage` 阶段变更 | `tran:edit` | **核心写操作，直接影响成交金额统计** |
| 交易备注 CRUD | `tran:view/edit/delete` | 同线索备注 |

**涉及文件**：`ClueController.java`(+31/−2)、`TranController.java`(+41/−10)、`CustomerController.java`(+16/−2)

### P0-2 SQL 注入：`${filterSQL}` 外部可控

**根因链**：`TActivityMapper.xml` / `TUserMapper.xml` 用 `${filterSQL}`（字符串拼接，非预编译）。`filterSQL` 定义在 `BaseQuery`，`ActivityQuery` 等继承它，经 `@ModelAttribute` 绑定时攻击者可传 `?filterSQL=or 1=1...`。`DataScopeAspect` 对**非 admin** 会覆盖该值，但 **admin 分支完全不处理**——注入值直达 SQL。

**修复（双层纵深防御，任一层独立生效）**：

1. **第 1 层** — 新建 `SecureBinderAdvice`：`@InitBinder` + `setDisallowedFields("filterSQL")`，在 Web 绑定层全局拒收该字段。任何 Controller、任何 Query 子类都无法再被外部写入。
2. **第 2 层** — `DataScopeAspect` 补 admin 分支 `setFilterSQL(null)`，兜底保证「进入 SQL 的过滤片段只能由切面生成」。

> **为何不把 `${}` 改成 `#{}`**：`filterSQL` 是动态 **SQL 片段**（`and ta.owner_id=5`）而非值，参数化会破坏数据权限功能本身。字段级拒收才是正解。

**涉及文件**：`SecureBinderAdvice.java`(新建 33 行)、`DataScopeAspect.java`(+6)

### P0-3 JWT 泄露密码哈希

**根因**：`MyAuthenticationSuccessHandler` 把**整个 `TUser`**（含 `loginPwd` 的 BCrypt 哈希）序列化进 JWT payload。JWT 只 base64 编码**不加密**，任何持 token 者（浏览器插件 / XSS）解码即可离线爆破。

> 关键排查点：`TUser.loginPwd` 字段本身的 getter `getLoginPwd()` 并**无** `@JsonIgnore`（只有 Spring Security 的 `getPassword()` 上有），所以确实会被序列化进 payload。

**修复**：
- 序列化前 `tUser.setLoginPwd(null)`。密码只在 DB 存储、只在登录时由 `DaoAuthenticationProvider` 内存比对，token 内无须保留凭证。
- 保留 `roleList` / `permissionList`——已先 grep 确认 `TokenVerifyFilter` 重建权限与 `DataScopeAspect` 判定 admin 都依赖它们，不可剥离。
- `JWTUtils.createJWT(userJSON, expireSeconds)` 增加 `withExpiresAt`，TTL 与 Redis 会话同源，防「僵尸 token」（旧版 JWT 无过期声明，生死全靠 Redis）。

**实测验证**：解码线上 JWT payload 确认 `jwtHasLoginPwd: false`、`jwtExp: "2026/9/10 12:53:29"` ✅

**涉及文件**：`MyAuthenticationSuccessHandler.java`(+15/−5)、`JWTUtils.java`(+13/−1)

### P1-1 权限指令 N+1 请求风暴

**根因**：`main.js` 的 `v-hasPermission` 指令内部**每个按钮都独立** `doGet('/api/login/info')`。一个页面十几个权限按钮 ＝ 十几个并发请求同一接口。

**修复**：`util.js` 新增 sessionStorage 权限缓存（`get/set/clearPermissionCache`）；`main.js` 用**单飞 Promise（single-flight）**重写指令——命中缓存零请求，未命中则复用同一 in-flight Promise，无论多少按钮同时挂载只发 1 次；结果转 `Set` 做 O(1) 判定。

**防串号设计**：把 `clearPermissionCache()` 内联进 `removeToken()`——登出、异地踢下线、令牌失效都走该函数，单点收口。用 sessionStorage 而非 localStorage：会话级隔离，关标签页自动失效。

**涉及文件**：`main.js`(+41/−16)、`util.js`(+52)

### P1-3 异常体系：响应回吐堆栈

**根因**：`GlobalExceptionHandler` 用 `R.FAIL(e.getMessage())` 把 SQL 报错细节（表名、字段、驱动栈、内部类名）直接返回前端（CWE-209 信息泄露）。但 Service 层又用 `throw new RuntimeException("手机号已存在")` 承载**面向用户的业务文案**，两类异常混用同一通道，处理器无法区分。

**修复（异常二分体系）**：
- 新建 `BusinessException`：业务规则失败，message 面向用户 → **透传**，`warn` 级日志。
- 其余 `Exception`：系统故障 → 响应**统一脱敏**为「服务器繁忙，请稍后重试」，完整堆栈仅落服务端 `error` 日志。
- 新增 `MethodArgumentNotValidException` / `MissingServletRequestParameterException` / `MethodArgumentTypeMismatchException` 专项处理，给字段级友好提示。

> 实测复现的原始报错：`DELETE /api/clue/batch?ids=abc` 会把 `Validation failed for argument [0] in public com.cyk.result.R com.cyk.web.TranController.addTran(...)` 整段长文回吐前端，既泄露内部类名又不友好。

配套将 `CustomerManager`、`ClueServiceImpl`、`TranServiceImpl`（阶段变更 3 处）的 `RuntimeException` 改为 `BusinessException`。

**涉及文件**：`GlobalExceptionHandler.java`(+67/−1)、`BusinessException.java`(新建)、`CustomerManager.java`(+7/−1)、`ClueServiceImpl.java`(+8/−4)

### 2-2 后端：补齐搜索筛选能力（「功能模糊」的根因）

**关键诊断**：线索 `selectClueByPage(Integer current)` 只收页码、客户 `selectCustomerPage()` **无任何入参**——后端根本没有查询条件入口。因此前端无论做多漂亮的搜索栏都**无法生效**。

| 模块 | 改造 | 新增筛选维度 |
|------|------|-------------|
| 线索 | `selectClueByPage(@Param("query") ClueQuery)` + SQL 动态 `<where><if>` | 姓名/手机（like）、负责人、活动、称呼、贷款、意向状态、意向产品、来源（等值）、**`converted` 布尔（已转客户/仍在跟进）** |
| 客户 | `selectCustomerPage(@Param("query") CustomerQuery)` | 姓名/手机（like）、负责人、活动、选购产品、来源、意向状态 |
| 交易 | `selectTranByPage(@Param("query") TranQuery)` | **`stage` 阶段筛选（销售管道核心，旧版完全缺失）**、`tranNo` 流水号 like、`money` 金额阈值 |

**三项严谨性设计**：

1. **向后兼容**：所有 `<if>` 以 `query != null and ...` 打头。`selectCustomerPage` 还被 `TranServiceImpl.getCustomerOptions()` 复用（交易页客户下拉需全量），传 `null` 即退化为无筛选查询，不影响既有调用方。
2. **确定性排序**：旧版 SQL 无 `order by`，结果顺序由 MySQL 存储引擎决定，**翻页可能出现重复行或漏行**。统一补 `create_time desc, id desc`（id 次级兜底防同时刻批量导入抖动）。
3. **金额语义修正**：交易旧版为 `tt.money = #{money}` **等值匹配**——金额是 BigDecimal 连续值，等值查询几乎不可能命中，那个搜索框实际上是废的。改为 `>=` 阈值语义，与本项目活动模块既有的 `cost >= budget` 约定保持一致。

**附带安全加固**：`TranQuery` 新增 `tranNo` 检索字段后，因 `TTran` 有同名字段，`BeanUtils.copyProperties` 会把外部值带入 UPDATE。已在 `TranServiceImpl.updateTran` 显式 `setTranNo(null)`——流水号是 Redis 原子序列生成的业务主键，不可由编辑接口篡改。**（已核实 `saveTran` 在拷贝后无条件覆盖 tranNo，新增场景同样安全）**

### 2-3 前端：三个列表页重构

统一结构：**页面 Hero（eyebrow+标题+职责说明+运行状态徽标）→ 概览指标条 → 筛选面板 → 卡片化表格 → 完整分页**。

| 改造点 | 原状态 | 新状态 |
|--------|--------|--------|
| 页面标识 | 无标题、无说明，看不出模块职责 | Hero 区 + eyebrow（`JOURNEY · LEAD POOL` 等） |
| 数据感知 | 只有表格 | 4 个概览指标（总数/已转化/待跟进/已选中），筛选后语义切换为「匹配线索」 |
| 筛选能力 | 线索与客户**完全没有** | 6 项（线索）/6 项（客户）/4 项（交易），支持任意组合、回车即查 |
| 状态呈现 | 纯文本 | 语义化彩色标签；意向状态按「高/中/低」分档配色 |
| 逾期提醒 | 无 | 下次联系时间早于当前时刻 → 红色高亮 + 「逾期」标签 |
| 空态 | 空白表格 | 区分「没有数据」与「筛选无结果」，各给一键出口 |
| 分页 | `prev,pager,next`，无总数 | `total,prev,pager,next,jumper` + 跨页连续序号 |

**三项主动移除的缺陷设计**：

1. **页级 Map 缓存（`pageCache`）**：把每页结果永久缓存，仅靠增删改时手动 clear。但线索/交易是多销售共享数据，别人新增或阶段推进后，本页看到的仍是陈旧快照且用户无法主动刷新。**移除，改为每次真实拉取 + loading 反馈**（每页仅 10 条，开销可忽略，一致性优先）。

## 第三阶段 · 实测中暴露的深层缺陷（本阶段价值最高）

### 3-1 权限码从未播种 ⚠️ 我上一轮引入的回归

**现象**：补齐 `@PreAuthorize` 后实测，交易列表的「新建/批量删除」按钮消失，详情页「推进阶段/编辑/删除」全部消失。

**排查过程**：起初推断是「`t_role_permission` 绑定缺失」，但直连真实数据库（WSL Docker 内的 `dlyk-mysql`）查证后发现**完全不是**：

```
t_permission 共 59 行（42 条 type='button'）
  tran 模块只有    tran:list / tran:view                    ← 缺 tran:add / tran:edit / tran:delete
  customer 模块只有 customer:list/view/export               ← 缺 customer:delete
admin 在 t_role_permission 已绑定 59/59 —— 绑定表是完整的
```

**根因**：**缺的是被绑定的对象本身**。代码一直引用的这 4 条权限码，权限表里从未创建过。权限不存在 ⇒ 任何角色都无法被授予 ⇒ 功能永久死亡。

> 这意味着：`TranView.vue` 原始代码就写着 `v-hasPermission="'tran:add'"`，即交易的增删改按钮**在我接手前就永久不可见**；而「删除客户」是「按钮可见但点了必失败」。

**我的疏漏**：上一轮补 `@PreAuthorize` 时，只校验了前后端权限码是否**互相对齐**，却**从未核实这些码是否真实存在于权限表**。教训已记入仓库记忆：**加 `@PreAuthorize` 前必须核实权限码已播种**，否则会把「越权可用」变成「功能死亡」。

**修复**：
1. `server/db/permission_seed_fix.sql`（幂等，`NOT EXISTS` 守卫，`parent_id` 用 url 子查询解析不硬编码 id）补建 4 条权限。授权严格遵循既有设计边界：**admin 得全部 4 条；saler 仅得 `tran:add`/`tran:edit`，不含任何删除权**——实测 saler 现有 17 条权限中零 delete（连 `clue:delete` 都没有），删除属管理动作。
   > 更新（2026-09-11）：该脚本的成果已直接落入建库基线——补建的 4 条权限（`tran:add`/`tran:edit`/`tran:delete`/`customer:delete`，id 1112~1115）及其授权关系已逐字保留在 `server/db/ApexSales_data.sql` 中，新库重建即为完整状态；该独立脚本已不再需要，故删除。历史叙述保留供回溯。
2. 架构加固 `UserServiceImpl.resolveButtonPermissions()`：admin 角色隐式获得全部按钮权限码（新增 `TPermissionMapper.selectAllButtonCodes()`），与 `t_role_permission` 完整性**解耦**；普通用户仍严格按绑定生效（最小权限）。菜单树不受影响。

### 3-2 JWT 权限快照滞后（架构级安全隐患）

**现象**：权限播种后，`/api/login/info` 已返回 46 条，但后端 `@PreAuthorize` 仍拦。

**根因**：系统鉴权有**两条独立路径，生效时机不一致**：

| 路径 | 数据源 | 生效时机 |
|------|-------|---------|
| 前端 `v-hasPermission` | `/api/login/info` **实时查库** | 立即 |
| 后端 `@PreAuthorize` | `TokenVerifyFilter` 从 **JWT 载体**重建 SecurityContext | 签发时刻的快照，直到 token 过期 |

后果：管理员收走某人的角色后，该用户前端按钮消失、看似已失权，但**只要直接调接口，旧 token 仍按原权限放行**——最长可持续到 token 过期（普通会话 1 小时，勾选「记住我」**长达 7 天**）。这是撤权场景下的越权窗口。

**修复**：`assignRoles()` 改为返回「角色集合是否真的发生变化」，变化时调 `invalidateSessionIfRolesChanged()` 删除 Redis JWT key，强制重新登录换取新权限。与项目既有范式对齐（`aiUpdateUserRolesAndStatus` 禁用账号删 key、`deleteById` 删用户删 key）。

> **必须做变更检测的原因**：实测发现前端 `UserView` 的 `submitData = {...userForm.value}` **总是**携带 `roleIds`（未改动时为原值，无角色时为 `[]`）。若不检测变化就把失效逻辑放进 `assignRoles`，管理员**仅改名也会把用户踢下线**，属无谓打扰。用 `Set.equals` 比对可忽略顺序差异（`[1,2]` 与 `[2,1]` 视为未变化）。

**端到端实测（6 项断言全通过）**：

| 断言 | 结果 |
|------|------|
| 基线：qa_tester 无角色读线索 | `500` 权限不足 |
| admin 指派 saler 角色 | `200` |
| **变更后用旧 token 立即访问** | **`903`** ✅ 越权窗口从最长 7 天缩短为**即时** |
| 重新登录后新 token 读线索/交易 | `200` 新权限即时生效 |
| **提交相同 roleIds 后旧 token** | **`200`** ✅ 变更检测正确，不误踢 |
| admin 自身 token / 恢复现场 | `200` 未被误伤、已复原 |

### 3-3 字典 `order` 字段全为 null（既有底层缺陷）

**现象**：交易阶段时间轴显示 `01创建→06丢失关闭→04产品检验→02确认清单→03交付定金→05付款成交`，明显错序。

**排查**：查数据库发现 `t_dic_value.order` **明明有值**（stage 为 `1,3,4,5,6,7`），但 `/api/dicvalue/stage` 返回的 `order`/`typeCode`/`remark` **全是 `null`**，只有 `id` 与 `typeValue` 有值。

**根因**：`TDicTypeMapper.selectByAll`（字典全量缓存 `cacheMap` 的唯一数据源，`DataTask` 每 180 秒刷新）SQL 只 select 了 `tdv.id dicId, tdv.type_value dicName` 两列，resultMap `<collection>` 也只映射这两列。

> **模型有字段 ≠ SQL 查了该列 ≠ resultMap 映射了该列**——三层任一断裂都会静默变 null，不报错。

**双向致命后果**：
1. 有序字典排序退化为**按 id 排序** → 时间轴错序；
2. 相邻阶段判定 `s.order === currentStage.order - 1` 变成 `null === NaN` **恒为 false** → `prevStage`/`nextStage` 永远 null → **交易详情页的「推进/回退阶段」按钮在我改造之前就从未能渲染出来**。

**修复**：SQL 补 `` tdv.`order` dicOrder ``（`order` 是 MySQL 保留字，必须反引号）+ `type_code` + `remark`；resultMap 补 3 个映射；并加 `order by tdt.id, tdv.`order`, tdv.id` 让**源头就有序**，不再依赖各调用方自行排序（各前端 `.sort()` 写法不一，且 order 为 null 时排序本就失效）。

**实测验证**：

|----|-------|-------|
| `order` 字段 | 全 `null` | **1,3,4,5,6,7** ✅ |
| `typeCode` | 全 `null` | `'stage'` ✅ |
| 时间轴顺序 | 01→06→04→02→03→05 | **01→02→03→04→05→06** ✅ |

### 3-4 SQL NULL 三值逻辑（我自己引入的 bug）

**现象**：线索筛选 `converted=true` → 8 条，`converted=false` → 22 条，但总数 **65**。`8 + 22 = 30 ≠ 65`，**静默缺口 35 条**。用户选「仍在跟进」期望 57 条，却只看到 22 条。

**根因**：`and tc.state != -1` 遇 `state IS NULL`（实测 65 条中 **35 条**为 NULL）时，`NULL != -1` 结果是 **UNKNOWN** 而非 TRUE，在 WHERE 中按 FALSE 处理 → 35 条被静默丢弃。

> 这类 bug **最隐蔽——不报错、只悄悄漏数据**。我发现它靠的是一个不变量：**分片筛选结果之和必须等于总数**，对不上就一定漏了 NULL 分支。

**修复**：`and COALESCE(tc.state, 0) != -1`（把 NULL 归一为 0，不可能等于魔法值 −1）。业务语义上「未设置状态」本就属于「尚未转化，仍在跟进」。

**实测验证**：`65 = 8(已转) + 57(在跟进)`，`sumsToTotal: true` ✅（修复前 8+22=30）

**涉及文件**：`TClueMapper.xml`

### 4-6 外键 RESTRICT 被当作「数据库操作失败」（删字典类型/删字典值/删用户）

**现象（实测 + 日志复现）**：
- 删除带字典值的类型 → 500（`t_dic_value.type_code` RESTRICT）；
- 删除被 11 处业务列引用的字典值（`t_tran.stage`、`t_clue.state` 等）→ 500；
- 删除名下有活动的用户 → 500（`run-backend.log` 612 行留有 `t_activity_ibfk_1` 现场）。

**根因**：三处删除都是裸调 Mapper，`SQLIntegrityConstraintViolationException` 落入兜底 → 用户只看到「数据库操作失败」，不知道**为什么**失败、**该怎么做**。RESTRICT 本是业务语义（"数据仍被引用"），被错误地当成技术故障吞掉。

**修复（按业务语义分流）**：
| 场景 | 策略 | 提示 |
|------|------|------|
| 删字典类型 | **前置拦截**（先 `countByTypeCode`） | 「该字典类型下仍有 N 个字典值，请先删除后再操作」 |
| 删字典值 | **捕获转译**（引用方 11 处、逐个前置统计不现实） | 「该字典值已被业务数据引用，无法删除」 |
| 删用户 | **捕获转译 + 引导替代方案** | 「该账号名下仍关联业务数据，无法直接删除；如需停用请改为『禁用账号』」 |

> CRM 语义下负责人/创建人**不应连带删除业务数据**，故不做级联删除；捕获 `DataAccessException` 后 `log.warn` 留痕（含 id）+ `BusinessException` 透传友好文案（配合第一阶段异常二分体系）。

**实测验证**：删带值类型 → `msg=该字典类型下仍有 1 个字典值` ✅；批量删含被引用账号 → 事务回滚 + 同口径提示 ✅
